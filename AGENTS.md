# Agent guidance

## Project

`prpr` monitors open pull requests authored by the active GitHub CLI account, including drafts, across repositories visible to that account, and open pull requests that request the account's review directly (`user-review-requested:@me`), or did before the account reviewed them; team requests are excluded.

- `cmd/prpr/main.go` wires configuration, the GitHub client, and the Bubble Tea program.
- `internal/github` invokes `gh` and decodes GitHub API responses; `bots.go` parses the bot list and derives each bot's review state; `accounts.go` lists gh's accounts, pins one, and passes its token to gh commands; `reviewed.go` finds pull requests the viewer already reviewed and places each one with a `ReviewStatus`; `readiness.go` selects the fields only ready-to-merge rules read (`Needs`) and runs the required checks query.
- `internal/readiness` owns ready-to-merge rules: their conditions, evaluation, and JSON.
- `internal/tui/accounts.go` owns the account picker and switching the pinned account.
- `internal/preferences` stores each account's scope (one repository, a watchlist, or All) and its watchlists, and the app settings: the pinned account, icon set, whether the legend is open, and ready-to-merge rules.
- `internal/tui/model.go` owns app transitions and scope state.
- `internal/tui/repository_picker.go` owns repository-picker input and requests.
- `internal/tui/watchlists.go` owns watchlist editing in the picker: marks, the name input, and saving, renaming, and deleting watchlists.
- `internal/tui/pr_pane.go` owns the two pull-request panes: focus, layout, per-pane selection, and the page indicator.
- `internal/tui/quota.go` owns rate-limit polling and the status line.
- `internal/tui/changes.go` owns change tracking between refreshes: row marks, changed cells, and gone pull requests.
- `internal/tui/mouse.go` owns mouse mode: mapping screen lines to panes and rows, hover, clicks, and the wheel.
- `internal/tui/attention.go` owns the attention summary line: its numbered categories, their counts, and category filters.
- `internal/tui/filters.go` owns search and quick filters: matching, the search input, and the active-filter text.
- `internal/tui/details.go` owns the details screen (a Lip Gloss layer over the list on large terminals, full screen otherwise) and the wording of each status.
- `internal/notifier` posts desktop notifications through the system's notifier command where one can reach the desktop.
- `internal/tui/title.go` owns the terminal title and its flashing.
- `internal/tui/notify.go` owns notifications: the transitions that alert, their text, and the OSC 9 command.
- `internal/tui/open.go` owns opening the selected pull request in the browser and copying its URL, and the status-line notice they set.
- `internal/tui/pr_table.go` owns pull-request table columns, statistics cells, and links.
- `internal/tui/rules.go` owns applying the rules (`ready`, the Merge cell, the details' **Ready** row) and the `,` rule editor, a `huh` form.
- `internal/tui/icons.go` owns the Unicode and Nerd Font icon sets and the `i` toggle.
- `internal/tui/legend.go` owns the `L` icon legend panel docked under the lists: its sections and how many fit.
- `internal/tui/keys.go` owns key bindings, their enabled state, and per-screen help.
- `docs/demo` is a separate Go module that records `docs/demo.gif` against a fake `gh` with made-up data; see CONTRIBUTING.md.
- `.github/scripts/package-manifests.sh` writes the Homebrew formula and Scoop manifest that the release workflow publishes to the `homebrew-tap` repository.

## Development commands

Use Go 1.26 or later:

```sh
go run ./cmd/prpr
go build -o /tmp/prpr ./cmd/prpr
go test ./...
go test -race ./...
go vet ./...
gofmt -l cmd internal
```

Running the app requires `gh` on `PATH`, authenticated to `github.com`. Package checks do not require GitHub credentials or a live network connection. See [CONTRIBUTING.md](CONTRIBUTING.md) for setup and verification details. When raising the minimum Go version, update `go.mod`, the README, this guide, and the Go version in both CI and release workflows together. Release builds stamp the tag into `main.version` through `-ldflags`; keep that variable name.

## Contracts to preserve

- Do not store GitHub tokens. Runtime GitHub access goes through a `gh` account: the active one, or one pinned by login. A pinned account's token is read with `gh auth token --hostname github.com --user <login>` at the start of each fetch, held only in `github.Client` as a `secret` that formats as `[redacted]`, and passed to gh API commands as `GH_TOKEN` in the child environment (never an argument), with inherited token and debug variables dropped. Error text is scrubbed of it. Login, token reads, account listing, and the browser never receive it. A pinned account that gh cannot give a token for is an `AuthError`; never fall back to another account. An environment `GH_TOKEN` or `GITHUB_TOKEN` disables pinning.
- The pinned login is saved under the preferences file's `app` key, which no account key can collide with. Account discovery reads `gh auth status --hostname github.com --json hosts`, skipping environment-token entries; never parse its text output. Each account choice increments `accountGeneration`; fetch, preview, and quota results from an older generation are dropped (a stale quota read still continues the poll chain).
- Preserve the authored, open pull-request query, pagination, updated-descending fetch order, and draft status. **My PRs** is displayed ready-to-merge first (the same rule that colors the Merge column green), then oldest `createdAt` first, ties in fetch order; **Review requested** is displayed in three groups, each in fetch order (see the reviewed query below).
- Preserve the review-request query `is:pr is:open user-review-requested:@me archived:false sort:updated-desc`. Both lists are fetched and replaced together.
- A full fetch also runs the reviewed query `is:pr is:open reviewed-by:@me -author:@me archived:false updated:>=<30 days ago> sort:updated-desc`; all three queries, and the required checks query when a rule needs it, succeed or the fetch fails. It keeps only pull requests whose `ReviewRequestedEvent`s named the viewer directly, and a pull request also pending in the request list stays a request. `github.ReviewStatus` places each one by the first match: no review of the viewer's among the latest `activityItems` timeline reviews and comments (new activity); the viewer's latest review dismissed; draft; no review of the viewer's at `headRefOid` (new commits; compare oids, never dates); an author comment or review after the viewer's latest review or comment (author replied; other people never count); latest non-comment review approved (approved); otherwise waiting on author. **Review requested** lists pending requests, then reviewed rows that need the viewer, then waiting rows, each in fetch order. Waiting rows are drawn dim and italic, always with their status text before the name, and never count toward category 6. Previews never run the reviewed query.
- A missing saved account choice is different from a saved empty repository value: missing prompts for a choice; empty means the user explicitly chose All repositories. Restoring a saved choice must not write preferences. `chooseScope` (and `chooseRepository`) is the explicit commit-and-save path.
- A watchlist is a name (trimmed, at most 40 characters, unique ignoring case) and a non-empty set of exact `owner/repo` names. An account's value stays a plain repository string unless it has watchlists or a watchlist scope; then it is an object with `repository` or `watchlist` and `watchlists`, and an object with neither has no saved scope. A saved scope naming a missing watchlist prompts again. Deleting the watchlist in scope saves All; renaming it keeps the scope on it. Replacing another watchlist by name needs a second Enter, and deleting one a second Ctrl+D.
- Preference-save failures are nonfatal: keep the in-session selection and show the warning.
- With no rows on screen, a fetch also runs `Client.Preview`, which selects only fast fields (no `mergeStateStatus`, timeline, checks, reviews, or bots). Its rows show `…` for unknown cells and are dropped when the fetch finishes, fails, or was replaced. Previews never become the change baseline. Refreshes do not preview.
- Keep both panes' previous rows visible during a refresh only while the refresh indicator is shown, and clear them when a fetch fails; do not show stale results as current.
- Keep picker cancellation and request-ID checks so obsolete asynchronous results cannot change current state.
- Every fetch start increments `refreshGeneration`; auto-refresh ticks from an older generation are ignored, so any refresh restarts the timer. A due tick never closes the picker or skips the scope prompt; it reschedules instead. While successive full fetches leave a merge state in scope unknown, the next refresh comes after `unknownRecheckDelay`, doubling each time, never later than the interval; it is an ordinary full fetch. Authentication failures are not retried automatically, except that a pinned account rechecks gh's local token every `tokenRecheckInterval` and fetches only when the token differs from the one that failed; any fetch or account choice ends that wait. The title countdown is display only: each schedule starts a new once-a-second tick chain, and ticks from an older chain are dropped.
- Quota polling uses a GraphQL query that selects only `rateLimit`, which GitHub does not charge for. Do not use the REST `rate_limit` endpoint: its graphql resource does not track points spent by GraphQL queries. Polling runs as a single chain: each result schedules the next tick. It pauses during login or after an authentication failure and resumes after a successful fetch.
- Pull-request identity is the pane's visible-row index mapped through that pane's `visible` slice to its own source list (`PullRequests` or `ReviewRequests`). Rows after the visible ones are gone rows, mapped through the pane's `gone` slice to its `changes.gone` list. Do not identify rows by PR number alone.
- Change marks compare each successful fetch with the previous successful one, by repository and number, per pane. They pile up until the cursor leaves the row or `x` clears them; a failed fetch keeps the baseline, and an account switch resets it. Gone rows are the only results shown that are not current, and they must always be dimmed, struck through, and marked `−`. Age is never compared. Change state stays in memory.
- Mouse mode is off at start, toggled by `m`, and kept in memory only. Only the list screen requests mouse input; other screens leave it to the terminal. Hover never moves the cursor or clears marks; clicks and the wheel move the cursor through the same leave-row rule as keys. Hit testing follows `listLines` and finds a table's first drawn row from its selected row, since Bubbles does not expose its scroll position.
- Bubbles owns the pull-request table cursor and scrolling. Preserve ANSI/grapheme-aware width behavior and safe OSC 8 hyperlink targets. Cells end their colors with full resets, so row stripes and the selected-row background are re-applied after each reset when the table is drawn.
- Notifications are off unless `--notify` is given; `n` toggles them in memory. They compare each successful full fetch with the change baseline before it is replaced, so the first fetch of an account, previews, and failed fetches never alert. Authored pull requests alert only when listed in both fetches, on turning ready to merge by the rules (against the last known readiness, which an unknown result does not change; applying new rules re-records it, or drops it when they need fields not yet fetched, and never alerts), CI turning failing, or changes being requested; a review-pane row alerts when it joins the list or stops waiting, and never when it starts waiting. Only the repository scope applies. Each fetch sends at most one notification, built from `singleLine` text: through `internal/notifier` (`osascript` or `notify-send`, text passed as arguments, never as script source) when it can reach the desktop, else as OSC 9 (`ansi.Notify` through `tea.Raw`), never both. Either way it rings the bell and repeats the text as the status-line notice. A failed desktop notification switches the session to OSC 9.
- The terminal title (`tea.View.WindowTitle`, on unless `--title=false`, which also turns off `ReportFocus`) shows, by priority: a flashing alert, a fetch (`loading` until full rows are shown, else `refreshing`), an error, then the count of distinct in-scope pull requests in attention categories 1–3 and 6. Titles are single-line and stripped of escape sequences. A flash starts from the same alerts as notifications, whatever `notify` is, unless the terminal reported focus; it stops on focus, a key press, a click, or after `flashDuration`, and each flash or stop increments `flashGeneration`, so older ticks are dropped. The title spinner follows the clock at `titleSpinnerInterval`, not the list spinner.
- The Unicode icon set is the default and draws exactly what earlier versions drew. Nerd Font icons are opt-in (`--icons`, then `PRPR_ICONS`, then the saved `icons` under the preferences file's `app` key, then Unicode), since terminals do not report their font. Every icon is one cell wide, but Nerd Font icons are often drawn wider, so a Nerd icon is always followed by a space or column padding, never directly by a number or mark. Status symbols (merge, CI, review, bots, State, reviewed status, attention categories, pin, bell, star, statistics headers) are drawn only through `iconSet`, so both sets cover them; change marks (`+ • · −`) and placeholders (`…`, `—`) are the same in both sets. The details screen, notifications, and help keep their words in both sets. The `L` legend (saved under the `app` key as `legend`) explains the symbols of the set in use, drawn through `iconSet` with the table's colors, so a new status symbol needs a legend entry too. It sits between the panes and the selected URL, so hit testing ignores it; it takes only lines the panes' current layout leaves above its smallest tables, never switching to one pane, shows whole sections only, and when none fit it hides and the title says so.
- `o` opens the selected row through `gh pr view --web -- <url>`, run asynchronously, or with an account pinned through `GH_BROWSER`, gh's `browser` setting, `BROWSER`, or the system opener, without the token; `y` copies its URL with OSC 52 (`tea.SetClipboard`). Both act on the focused pane's selected row, gone rows included, and refuse URLs that fail `safePullRequestURL`.
- Search and quick filters apply to both panes on top of the repository scope, gone rows included, and stay in memory. Preview rows never match the failing-CI or ready-to-merge filters. The title line always names active filters, and Esc on the list clears them.
- Attention categories are fixed predicates over existing status fields, numbered 1–7 for good; there is no score. Unknown merge state is its own category and never counts as ready; null decisions and rollups never count as changes requested or failing. Counts follow the repository scope only, skip gone rows, and in a preview count conflicts alone. A category filter replaces the quick filter and limits its own pane; other panes show nothing. The summary line sits under the title when the terminal has at least `minSummaryHeight` lines, and layout and hit testing count it.
- The details screen describes the focused pane's selected row and moves through the same leave-row rule. Its merge text names a blocker only when the data proves it: a review decision (set only when reviews are required) can be named; checks never are, since required checks are not fetched. Preview rows show loading text for detail fields.
- Ready to merge is decided only by `readiness.Rule.Evaluate`, through the rules of the repository's owner (case-insensitive), else the default rule, which is the merge button alone: a `mergeStateStatus` of `CLEAN`, `HAS_HOOKS`, or `UNSTABLE`. Drafts, conflicts, and an unknown merge state always block, whatever the rule; a condition whose data is missing or cut short is unknown, never met. Rules apply to **My PRs** only, which alone selects their fields, and only while some rule needs them (`github.Needs`); review rows use the merge-button rule. Required checks come from `isRequired`, which GitHub answers only for a named pull request, so a follow-up query batches node IDs as variables and skips drafts and conflicts. Code owners are approved when no `asCodeOwner` review request is pending; an unnamed one is still pending. The Merge column is green when the rules hold and yellow when only the merge button does. Rules are saved under the preferences file's `app` key as `ready`; an unknown condition makes them unreadable, so the defaults apply with a warning and the file keeps them as written until rules are saved. The rule editor takes every key but Ctrl+C, Esc closes it without saving, and it never requests the mouse.
- GitHub's merge button (`mergeReady`: the default rule, review rows, and the yellow check) needs a `mergeStateStatus` of `CLEAN`, `HAS_HOOKS`, or `UNSTABLE`. `mergeable` alone says nothing about required reviews or checks. Conflicts win over every other state, drafts come from `isDraft` (the `DRAFT` state is deprecated), and an unknown or missing state is never shown as mergeable.
- Age is ready-for-review time (last `ReadyForReviewEvent`, else `createdAt`; zero for drafts), or for review requests the latest `ReviewRequestedEvent` naming the viewer with that ready time as fallback. Null review decisions and check rollups are unknown, never approved or passing.
- Statistics columns drop in reverse priority (Size, Comments, Review, CI, Bots, Age) before squeezing the PR name below `minStatsNameWidth`.
- Every configured bot is judged by one rule, with no bot-specific text parsing: unresolved, non-outdated threads it started are concerns; then a matching head-commit check run that is unfinished or failed; then whether its latest review, comment, or non-👀 reaction is at or after the head commit date. With no bots configured, queries select none of the bot fields.

## Tests and interactive changes

- Follow existing tests: literal JSON decoder fixtures, direct TUI-message tests, and real preference stores under `t.TempDir()`.
- Assert deterministic, consumer-visible behavior. Do not pin prose, screenshots, incidental formatting, or implementation details.
- TUI behavior changes require a real terminal/PTY smoke in addition to unit tests. Exercise selection, empty scopes, resize, picker cancellation, and links as relevant to the change.
- Do not perform live login or mutate a developer's GitHub or user configuration during checks.
- For isolated Linux smoke runs, put a fake `gh` first on `PATH` and use a temporary absolute `XDG_CONFIG_HOME`. An explicitly requested live, read-only smoke must preserve the existing GitHub CLI configuration with `GH_CONFIG_DIR`.

## Change discipline and repository hygiene

- Reuse existing helpers and components. Keep changes scoped; add an SDK, alternate credential store, compatibility alias, or framework only for a concrete requirement.
- Never force-add `.devcontainer/project-adhd`, generated environment files, credentials, binaries, or preference files. Keep personal PR and repository data out of public commits.
- Do not add instructions tied to an agent vendor or local development setup. Do not make GitHub mutations or commit/push unless the user requests them.
