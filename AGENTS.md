# Agent guidance

## Project

`prpr` monitors open pull requests authored by the active GitHub CLI account, including drafts (hidden unless `D` shows them), across repositories visible to that account, and open pull requests that request the account's review directly (`user-review-requested:@me`), or did before the account reviewed them, or whose author nudged the account with prpr; team requests are excluded. Authored pull requests in a merge queue (Trunk or GitHub's) are listed apart, in a **Merge queue** pane, and snoozed ones of either list in a **Snoozed** pane.

- `cmd/prpr/main.go` wires configuration, the GitHub client, and the Bubble Tea program.
- `internal/github` invokes `gh` and decodes GitHub API responses; `bots.go` parses the bot list and derives each bot's review state; `accounts.go` lists gh's accounts, pins one, and passes its token to gh commands; `reviewed.go` finds pull requests the viewer already reviewed and places each one with a `ReviewStatus`, reads nudges from review rows' timelines, and builds and decodes the mentions search; `nudge.go` owns the nudge comment format (`FormatNudge`, `parseNudge`) and finds a row's active nudge; `merged.go` lists the viewer's most recently merged pull requests; `queue.go` reads merge queue entries: GitHub's `mergeQueueEntry` and Trunk's comment (`trunk-io`, `<!-- Trunk Merge -->`), and parses queue names for the saved `queues` setting; `readiness.go` selects the fields only ready-to-merge rules read (`Needs`) and runs the required checks query. `notifications.go` reads `gh api -i notifications` (keeping stdout when gh exits 1 on a 304) and classifies the answer. `incremental.go` runs incremental fetches: signature queries, detail reads by node ID, and the cache.
- `internal/readiness` owns ready-to-merge rules: their conditions, evaluation, and JSON.
- `internal/tui/accounts.go` owns the account picker and switching the pinned account.
- `internal/preferences` stores each account's scope (one repository, a watchlist, every repository of one owner, or All) and its watchlists, and the app settings: the pinned account, icon set, whether the legend is open, whether the Merged list is collapsed, whether drafts are shown, the refresh and full refresh intervals, review bots, merge queues, how many merged pull requests to list, the editor `e` opens, and whether notifications, the mouse, the terminal title, and Live updates are on, ready-to-merge rules, and each account's snoozes and dismissed nudges.
- `internal/tui/model.go` owns app transitions and scope state.
- `internal/tui/repository_picker.go` owns repository-picker input and requests.
- `internal/tui/watchlists.go` owns watchlist editing in the picker: marks, the name input, and saving, renaming, and deleting watchlists.
- `internal/tui/pr_pane.go` owns the pull-request panes: per-pane selection, titles, the page indicator, the open panes (`openPanes`, `openPanesNeed`), their table heights (`openTables`), and the list chrome (`listChromeHeight`); `frame.go`'s `framePlan` combines them into which panes are drawn, their lines, and which can take focus.
- `internal/tui/pane_spec.go` holds `paneSpecs`: each pane's name, empty text, lists, tracker, layout flags (drawn only with rows, short, leftover, collapsible, attention, quick filters), columns, name tags, and `rowStyle`.
- `internal/tui/quota.go` owns rate-limit polling and the status line; `internal/tui/details.go`'s `rowStatus` words the selected row there.
- `internal/tui/watch.go` owns Live updates: the notifications chain, which threads are worth a fetch, and the pending follow-up fetch.
- `internal/tui/changes.go` owns change tracking between refreshes: row marks, changed cells and their direction and wording, gone pull requests, and when a mark counts as read.
- `internal/tui/mouse.go` owns mouse mode: mapping screen lines to panes and rows, hover, clicks, and the wheel.
- `internal/tui/attention.go` owns the attention summary line: its numbered categories, their counts, and category filters.
- `internal/tui/filters.go` owns search and quick filters: matching, the search input, and the active-filter text.
- `internal/tui/details.go` owns the details screen (a Lip Gloss layer over the list on large terminals, full screen otherwise) and the wording of each status.
- `internal/notifier` posts desktop notifications through the system's notifier command where one can reach the desktop.
- `internal/tui/title.go` owns the terminal title and its flashing.
- `internal/schedule` evaluates the weekly active-hours window and finds its next change; `internal/tui/schedule.go` owns sleeping and waking by it, the `S` editor, and `w`.
- `internal/tui/snooze.go` owns snoozing: the `z` form and typed times, wake signals and their comparison, waking (by fetch, timer, or `z`), undo (`U`), and the Snoozed pane's wake text.
- `internal/tui/notify.go` owns notifications: the transitions that alert, their text, and the OSC 9 command.
- `internal/tui/nudge.go` owns the nudge in effect on review rows: dismissals and `X`, the marker and its blink in the mark column, and the order of **Review requested**.
- `internal/tui/rerequest.go` owns `R`: nudging reviewers of an authored pull request, and its notices; `rerequest_list.go` owns its form: the grouped people, their keys, the urgency and note, and the team panel. `internal/github/reviewers.go` lists who can be nudged, with the author's past nudges, and posts the nudge.
- `internal/tui/reviewers.go` owns the details' Reviewers and Teams rows of authored pull requests: their lookup, its cache, and each team's standing.
- `internal/tui/shared.go` finds the repository or owner every row shares, which the tables leave out and the title names.
- `internal/tui/merged.go` owns the Merged pane's helpers: which pull requests moved there rather than going, the Recently merged setting, and its details text.
- `internal/tui/open.go` owns opening the selected pull request in the browser or an editor and copying its URL, and the status-line notice they set.
- `internal/tui/pr_table.go` owns building and redrawing tables, cell styles, and links; `columns.go` owns `columnSpec`, `layoutColumns`, and `buildRows`.
- `internal/tui/settings.go` owns the `,` Settings screen: its rows, keys, the bots field and queue checklist; `settings_apply.go` applies and saves each setting.
- `internal/tui/rules.go` owns applying the rules (`ready`, the Merge cell, the details' **Ready** row) and the rule editor (opened from Settings), a `huh` form.
- `internal/tui/icons.go` owns the Unicode and Nerd Font icon sets and the `i` toggle.
- `internal/tui/legend.go` owns the `L` icon legend panel docked under the lists: its sections and how many fit.
- `internal/tui/keys.go` owns key bindings, their enabled state, per-screen help lines, and the help overlay's groups; `internal/tui/help.go` owns drawing the help line and the `?` overlay.
- `docs/demo` is a separate Go module that records `docs/demo.gif` against a fake `gh` with made-up data; see CONTRIBUTING.md.
- `.github/scripts/package-manifests.sh` writes the Homebrew formula and Scoop manifest that the release workflow publishes to the `homebrew-tap` repository.

## Development commands

Use Go 1.26 or later:

```sh
go run ./cmd/prpr
go build -o /tmp/prpr ./cmd/prpr
go test ./...
go test -race ./...
go vet ./...
gofmt -l cmd internal
```

Running the app requires `gh` `github.MinimumVersion` (2.81.0, for `gh auth status --json`) or later on `PATH`, authenticated to `github.com`; startup runs `gh --version` and stops with a `VersionError` for an older one, and carries on when it cannot read the version. When prpr starts using a newer `gh` flag, raise `MinimumVersion` and the README requirement together. Package checks do not require GitHub credentials or a live network connection. See [CONTRIBUTING.md](CONTRIBUTING.md) for setup and verification details. When raising the minimum Go version, update `go.mod`, the README, this guide, and the Go version in both CI and release workflows together. Release builds stamp the tag into `main.version` through `-ldflags`; keep that variable name.

## Contracts to preserve

- Do not store GitHub tokens. Runtime GitHub access goes through a `gh` account: the active one, or one pinned by login. A pinned account's token is read with `gh auth token --hostname github.com --user <login>` at the start of each fetch, held only in `github.Client` as a `secret` that formats as `[redacted]`, and passed to gh API commands as `GH_TOKEN` in the child environment (never an argument), with inherited token and debug variables dropped. Error text is scrubbed of it. Login, token reads, account listing, and the browser never receive it. A pinned account that gh cannot give a token for is an `AuthError`; never fall back to another account. An environment `GH_TOKEN` or `GITHUB_TOKEN` disables pinning.
- The pinned login is saved under the preferences file's `app` key, which no account key can collide with. Account discovery reads `gh auth status --hostname github.com --json hosts`, skipping environment-token entries; never parse its text output. Each account choice increments `accountGeneration`; fetch, preview, and quota results from an older generation are dropped (a stale quota read still continues the poll chain).
- Preserve the authored, open pull-request query, pagination, updated-descending fetch order, and draft status. **My PRs** is displayed ready-to-merge first (the same rule that colors the Merge column green) and drafts last, then oldest `createdAt` first, ties in fetch order; **Review requested** is displayed urgent nudges first, then pending requests, then rows that need the viewer, then waiting rows, rows with a nudge in effect first within each group, otherwise in fetch order (`sortReview`; see the reviewed query and nudges below).
- Preserve the review-request query `is:pr is:open user-review-requested:@me archived:false sort:updated-desc`. Both lists are fetched and replaced together.
- A fetch is complete (the queries above) or incremental; both are full fetches in this guide's sense and return every list in full, so the TUI never knows which ran. Incremental: the same three searches at 100 per page, and the mentions search as one page of `mentionsLimit` (never paginated), select only `id url updatedAt headRefOid mergeable isDraft`, the head rollup state, and `mergeQueueEntry { state }` with GitHub's queue; a pull request's detail is read again (by node ID, aliases `p<i>: node(id: $id<i>)`, `detailBatch` at a time, each list with its own fields) when its list's cache lacks it, its signature differs, or it is in transition (`inTransition`: merge state unknown, CI pending, expected, failing, or erroring, held by a queue, a bot running, stale, or with concerns, unresolved threads when known), except a mentions row the cache keeps as dropped, which only a changed signature reads again; required checks run only for re-read authored rows. The cache keeps rows before `mergeReviews`, the reviewed and mentions searches' dropped rows included. The cache is keyed by viewer login: signatures naming another login make the fetch complete. A fetch is complete when the cache is empty: `ForceFull` (`r`), `UseAccount`, `SetBots`, `SetQueues`, a `SetNeeds` that changes the needs, any failed fetch, or `fullRefresh` (saved under `app`, default 15m, 0 never) passing since the last complete fetch. `cacheGeneration` keeps a fetch that started before a drop from writing the cache. A `null` node fails the fetch. Previews never touch the cache.
- A full fetch also runs the reviewed query `is:pr is:open reviewed-by:@me -author:@me archived:false updated:>=<30 days ago> sort:updated-desc`; so does the mentions query (below); all four queries, and the required checks query when a rule needs it, succeed or the fetch fails. It keeps only pull requests whose `ReviewRequestedEvent`s named the viewer directly, and a pull request also pending in the request list stays a request. `github.ReviewStatus` places each one by the first match: no review of the viewer's among the latest `activityItems` timeline reviews and comments (`activityField`, shared by the request, reviewed, and mentions searches, which reads comment bodies for nudges) (new activity); the viewer's latest review dismissed; draft; no review of the viewer's at `headRefOid` (new commits; compare oids, never dates); an author comment or review after the viewer's latest review or comment (author replied; other people and nudge comments never count); latest non-comment review approved (approved); otherwise waiting on author. `mergeReviews` returns pending requests, then reviewed and mentioned rows that need the viewer, then waiting rows, each in fetch order; the TUI orders them as above. Waiting rows are drawn dim and italic, always with their status text before the name, and never count toward category 6, except while a nudge is in effect, which undims them and counts them. Previews never run the reviewed query.
- A missing saved account choice is different from a saved empty repository value: missing prompts for a choice; empty means the user explicitly chose All repositories. Restoring a saved choice must not write preferences. `chooseScope` (and `chooseRepository`) is the explicit commit-and-save path.
- A watchlist is a name (trimmed, at most 40 characters, unique ignoring case) and a non-empty set of exact `owner/repo` names. An account's value stays a plain repository string unless it has watchlists or a watchlist scope; then it is an object with `repository` or `watchlist` and `watchlists`, and an object with neither has no saved scope. A saved scope naming a missing watchlist prompts again. An owner scope (`owner`, the object form, picked as `owner/*` from the owners of listed repositories) keeps rows whose repository owner matches ignoring case; it is a filter only, so queries are unchanged, and older versions read it as no saved scope. An account's object has at most one of `repository`, `watchlist`, and `owner`. Deleting the watchlist in scope saves All; renaming it keeps the scope on it. Replacing another watchlist by name needs a second Enter, and deleting one a second Ctrl+D.
- Preference-save failures are nonfatal: keep the in-session selection and show the warning.
- With no rows on screen, a fetch also runs `Client.Preview`, which selects only fast fields (no `mergeStateStatus`, timeline, checks, reviews, or bots). Its rows show `…` for unknown cells and are dropped when the fetch finishes, fails, or was replaced. Previews never become the change baseline. Refreshes do not preview.
- Keep each pane's previous rows visible during a refresh only while the refresh indicator is shown, and clear them when a fetch fails; do not show stale results as current.
- Keep picker cancellation and request-ID checks so obsolete asynchronous results cannot change current state.
- Every fetch start increments `refreshGeneration`; auto-refresh ticks from an older generation are ignored, so any refresh restarts the timer. A due tick never closes the picker or skips the scope prompt; it reschedules instead. While successive full fetches leave a merge state in scope unknown, the next refresh comes after `unknownRecheckDelay`, doubling each time, never later than the interval; it is an ordinary full fetch. Authentication failures are not retried automatically, except that a pinned account rechecks gh's local token every `tokenRecheckInterval` and fetches only when the token differs from the one that failed; any fetch or account choice ends that wait. The title countdown is display only: each schedule starts a new once-a-second tick chain, and ticks from an older chain are dropped.
- Quota polling uses a GraphQL query that selects only `rateLimit`, which GitHub does not charge for. Do not use the REST `rate_limit` endpoint: its graphql resource does not track points spent by GraphQL queries. Polling runs as a single chain: each result schedules the next tick. It pauses during login, after an authentication failure, or outside active hours, and resumes after a successful fetch; an account choice starts a new chain.
- Live updates (the saved `live`, `app` key, on unless false; Settings' **Live updates**) read `notifications?all=true` through `gh api -i` as the pinned account, with `If-Modified-Since` (a 304 costs no quota; gh exits 1 on it, so the status comes from the `-i` output), at most every `max(X-Poll-Interval, watchMinInterval)`. The first read of a chain is a baseline (one thread, never a fetch); later ones ask `since` the last baseline or 200's `Date`, so only GitHub's clock is compared. A thread updated after `since` is worth a fetch when it is a listed pull request, a `review_requested` or `mention` pull request not listed yet (unless an earlier fetch did not list it either, `watch.ignored`, as with team requests, until the account changes or the setting is toggled), or `ci_activity` in a repository of a listed authored pull request, all in the repository scope; a full page counts. It starts an ordinary fetch (`startAutomaticFetch`), or, while a fetch that began before the read was sent (`sentRefresh`) runs, one follow-up fetch (`watch.pending`). It is a signal only: auto-refresh keeps its interval, it never sets an error or notice, never marks notifications read, and makes no other request. Transient failures (401 included) back off, doubling, capped at the refresh interval (`watchMaxBackoff` when off); rate limits wait `RetryAfter`, at least `watchMinInterval`; a 403 is a rate limit only when `X-RateLimit-Remaining` is "0" or `Retry-After` is positive, and any other 403 and 404 are unsupported, which stop it (`unsupported`) until the account changes or the setting is turned off and on. It runs as one chain like the quota poll: `watch.generation` and `accountGeneration` drop older results, it pauses when `quotaBlocked` holds and resumes after a successful fetch, and starts only after an account's first successful fetch. The countdown adds `· live` while its last read was answered, and reads `live` alone with auto-refresh off.
- Pull-request identity is the pane's visible-row index mapped through that pane's `visible` slice to its own source list (`PullRequests` for My PRs and the Merge queue pane, which tell their rows apart by `inPane`, or `ReviewRequests`); `paneSnoozed` draws from both lists: its `visible` and `gone` indexes run over the authored list, then the review list (`splitIndex`), and each row uses its own list's change tracker (`trackerFor`). Fetched lists are named by `listID` (`listAuthored`, `listReview`, `listMerged`), never by a pane. Rows after the visible ones are gone rows, mapped through the pane's `gone` slice to its `changes.gone` list. Do not identify rows by PR number alone.
- Change marks compare each successful fetch with the previous successful one, by repository and number, per pane. They pile up until `x` clears them or the cursor leaves a row it read: a row is read once the cursor rested on it for `readDelay` (`restGeneration` drops rests the cursor left), or when details, `o`, or `y` showed it; a fetch that marks the row again makes it unread. A review row that turns to waiting on its author (`reviewedByViewer`: from a status not waiting to waiting or approved, so the viewer reviewed or commented) loses its mark instead of being marked. A failed fetch keeps the baseline, and an account switch resets it. A mark keeps the pull request as the first fetch that marked it found it (`was`); each changed cell is a `changeLine` from that value to the current one with a direction (good; bad for a failure, a request, or a conflict on an authored row, and on a review row only for its status turning to need the viewer, a request coming back, or gaining a nudge, a later normal or urgent one, or a raised urgency; else neutral), which colors the cell's underline and the row's marker (`▲`, `▼`, `•`), and words the status-line summary and the details' **Changed** row. Gone rows are the only results shown that are not current, and they must always be dimmed, struck through, and marked `−`. Age is never compared. Change state stays in memory.
- Mouse mode is off by default, follows the saved `mouse`, and is toggled by `m` or Settings. Only the list screen requests mouse input; other screens leave it to the terminal. Hover never moves the cursor or clears marks; clicks and the wheel move the cursor through the same leave-row rule as keys. Hit testing reads the same `framePlan` the list was drawn from and finds a table's first drawn row from its selected row, since Bubbles does not expose its scroll position.
- Bubbles owns the pull-request table cursor and scrolling. Preserve ANSI/grapheme-aware width behavior and safe OSC 8 hyperlink targets. Cells end their colors with full resets, so row stripes and the selected-row background are re-applied after each reset when the table is drawn.
- Settings (`,`) applies and saves each change at once; a failed save keeps it for the session. Removed flags (`--refresh`, `--bots`, `--queues`, `--notify`, `--icons`, `--title`) stop prpr with a message naming their setting; `PRPR_ICONS` is ignored. Changing bots or queues starts a full fetch (replacing a running one) whose result resets the change baseline (`settingsBaseline`) without marking, alerting, or waking snoozes, so unread marks and gone rows clear at that moment. A refresh change reschedules from now, except that during a running fetch or after an authentication failure it takes effect at the next fetch. Unreadable `refresh`, `fullRefresh`, `bots`, `queues`, `merged`, or `editor` values fall back to their defaults and stay in the file as written until saved; unreadable `notify`, `mouse`, `title`, `live`, or `mergedCollapsed` values stop prpr with the preferences error like other app values.
- Notifications follow the saved `notify` setting (off by default); `n` and Settings toggle and save it. They compare each successful full fetch with the change baseline before it is replaced, so the first fetch of an account, previews, and failed fetches never alert. Draft review rows never alert. Authored pull requests alert only when listed in both fetches, on turning ready to merge by the rules (against the last known readiness, which an unknown result does not change; applying new rules re-records it, or drops it when they need fields not yet fetched, and never alerts), CI turning failing, or changes being requested (a pull request a merge queue holds never turns ready to merge this way, and alerts on the other two only while Trunk shows it submitted, waiting on its checks); a review-pane row alerts when it joins the list or stops waiting, or on a nudge (`nudgeAlert`: a normal or urgent nudge in effect that is new, later, or of raised urgency; low never alerts, and `quiet` keeps waiting and `ReviewNudged` rows silent unless a normal or urgent nudge is in effect), and never when it starts waiting. An urgent nudge's title flash, a snooze woken by one included, lasts until focus, a key, or a click, not `flashDuration`, and a later flash replacing a lasting one lasts too. Snoozed pull requests never alert except when they wake. Only the repository scope applies. Each fetch sends at most one notification, built from `singleLine` text: through `internal/notifier` (`osascript` or `notify-send`, text passed as arguments, never as script source) when it can reach the desktop, else as OSC 9 (`ansi.Notify` through `tea.Raw`), never both. Either way it rings the bell and repeats the text as the status-line notice. A failed desktop notification switches the session to OSC 9.
- The terminal title (`tea.View.WindowTitle`, on unless the saved `title` is false, which also turns off `ReportFocus`) shows, by priority: a flashing alert, a fetch (`loading` until full rows are shown, else `refreshing`), an error, then the count of distinct in-scope pull requests in attention categories 1–3 and 6. Titles are single-line and stripped of escape sequences. A flash starts from the same alerts as notifications, whatever `notify` is, unless the terminal reported focus; it stops on focus, a key press, a click, or after `flashDuration`, and each flash or stop increments `flashGeneration`, so older ticks are dropped. The title spinner follows the clock at `titleSpinnerInterval`, not the list spinner.
- The Unicode icon set is the default and draws the same glyphs earlier versions drew. Nerd Font icons are opt-in (the saved `icons` under the preferences file's `app` key, else Unicode), since terminals do not report their font. Every icon is one cell wide except the nudge icons `nudgeLow`, `nudgeNormal`, and `nudgeUrgent` (👋 🔔 🚨, the same in both sets, drawn in the mark column, which widens to two cells while one is shown), but Nerd Font icons are often drawn wider, so a Nerd icon is always followed by a space or column padding, never directly by a number or mark. Status symbols (merge, CI, review, bots, the draft tag, reviewed status, attention categories, pin, bell, star, statistics headers) are drawn only through `iconSet`, so both sets cover them; change marks (`+ ▲ ▼ • · −`) and placeholders (`…`, `—`) are the same in both sets. The details screen, notifications, and help keep their words in both sets. The `L` legend (saved under the `app` key as `legend`) explains the symbols of the set in use, drawn by the table's own renderers, so a changed icon or color follows. `TestEveryIconIsInTheLegend` fails when an `iconSet` icon starts no legend entry: give a new icon an entry in `legendSections`, or a reason in `legendExempt`. A renderer that draws an existing icon for a new state needs a legend entry too; no test catches that. It sits between the panes and the selected URL, so hit testing ignores it; it takes only lines the panes' current layout leaves above its smallest tables, never switching to one pane, shows whole sections only, and when none fit it hides and the title says so.
- `o` opens the selected row through `gh pr view --web -- <url>`, run asynchronously, or with an account pinned through `GH_BROWSER`, gh's `browser` setting, `BROWSER`, or the system opener, without the token; `e` opens it in the saved `editor` (`app` key; VS Code's GitHub Pull Requests extension link `vscode://github.vscode-pull-request-github/open-pull-request-webview?uri=<url>` by default, VS Code Insiders, or github.dev) through `Client.OpenLink`, the same token-free opener, never gh; `y` copies its URL with OSC 52 (`tea.SetClipboard`). All three act on the focused pane's selected row, gone rows included, and refuse URLs that fail `safePullRequestURL`.
- Drafts are out of scope unless `showDrafts` (`D`, saved under the `app` key as `drafts`; off by default) is on: `inScope` is the repository scope plus that, so counts, the title, notifications, unknown rechecks, and pane totals skip hidden drafts, and pane titles count them through `inRepositoryScope`. Drafts, shown or hidden, count in no attention category and not in the title, and a draft review row never alerts; one alerts when it leaves draft. Shown authored drafts alert like other authored pull requests. Esc never changes it.
- Search and quick filters apply to every pane on top of the repository scope, gone rows included, and stay in memory. Preview rows never match the failing-CI or ready-to-merge filters. The title line always names active filters, and Esc on the list clears them.
- Attention categories are fixed predicates over existing status fields, numbered 1–7 for good; there is no score. Unknown merge state is its own category and never counts as ready; null decisions and rollups never count as changes requested or failing. Counts follow the scope only (the repository scope and hidden drafts), skip drafts even while shown and gone rows, and in a preview count conflicts alone. A category filter replaces the quick filter and limits its own pane; other panes show nothing. The summary line sits under the title when the terminal has at least `minSummaryHeight` lines, and layout and hit testing count it; at the same heights a faint rule (`footerRuleShown`) sits right above the selected URL, under whichever list or legend ends above it, and the layout counts it too.
- The details screen describes the focused pane's selected row and moves through the same leave-row rule. Its merge text names a blocker only when the data proves it: a review decision (set only when reviews are required) can be named; checks never are, since required checks are not fetched. Preview rows show loading text for detail fields. For a listed authored row (not preview, gone, review, or merged rows) the details add **Reviewers** and **Teams** from `Client.Reviewers`, the `R` query, looked up from `Update` while the details are shown, cached per pull request in memory until its `updatedAt` changes or `R` sends, a failed lookup tried again when the details next open, and results from an older `accountGeneration` dropped; both rows are always drawn, with the spinner (kept turning by `spinning`) while the lookup runs and a capped error when it failed; it never sets the notice. A team is pending (`reviewRequests`) or answered (`onBehalfOf` of a review not dismissed, since GitHub drops an answered team's request, and with it whether it was a code owner); `✓` means a member approved: the head commit for a pending team (as the `R` panel), any approval for an answered one; `◐` that members reviewed otherwise or are requested by name, else `✗`.
- Ready to merge is decided only by `readiness.Rule.Evaluate`, through the rules of the repository's owner (case-insensitive), else the default rule, which is the merge button alone: a `mergeStateStatus` of `CLEAN`, `HAS_HOOKS`, or `UNSTABLE`. Drafts, conflicts, and an unknown merge state always block, whatever the rule; a condition whose data is missing or cut short is unknown, never met. Rules apply to **My PRs** only, which alone selects their fields, and only while some rule needs them (`github.Needs`); review rows use the merge-button rule. Required checks come from `isRequired`, which GitHub answers only for a named pull request, so a follow-up query batches node IDs as variables and skips drafts and conflicts. Code owners are approved when no `asCodeOwner` review request is pending; an unnamed one is still pending. The Merge column is green when the rules hold and yellow when only the merge button does. Rules are saved under the preferences file's `app` key as `ready`; an unknown condition makes them unreadable, so the defaults apply with a warning and the file keeps them as written until rules are saved. The rule editor takes every key but Ctrl+C, Esc closes it without saving, and it never requests the mouse.
- GitHub's merge button (`mergeReady`: the default rule, review rows, and the yellow check) needs a `mergeStateStatus` of `CLEAN`, `HAS_HOOKS`, or `UNSTABLE`. `mergeable` alone says nothing about required reviews or checks. Conflicts win over every other state, drafts come from `isDraft` (the `DRAFT` state is deprecated), and an unknown or missing state is never shown as mergeable.
- Age is ready-for-review time (last `ReadyForReviewEvent`, else `createdAt`; zero for drafts), or for review requests the latest `ReviewRequestedEvent` naming the viewer with that ready time as fallback. Null review decisions and check rollups are unknown, never approved or passing.
- **My PRs** columns are the change mark, Merge, Repository (when it fits), Number, PR name, then statistics (there is no State column: a draft's name leads with `iconSet.draftTag`, and the name carries `cellState` changes); the **Merge queue** pane's are the change mark, Queue, Repository (when it fits), Number, PR name, Detail; **Review requested** has no Merge column (its change mark column widens to two cells while a row shows a nudge) and ends its fixed columns with Author after PR name; Repository and Author are sized to their longest value within caps; the **Snoozed** pane's are the change mark, Wakes, Repository (when it fits), Number, PR name, From; the **Merged** pane's are the change mark, Merged, Repository (when it fits), Number, PR name, Merged by. Repository is never drawn while one repository is in scope or `shared` (`shared.go`: every row the lists hold in scope, gone and merged rows included, search and filters ignored) finds one repository, which the title then names; a shared owner is dropped from repository cells and the narrow name prefix and named in the title unless the owner scope already says it. A dropped gone row that changes `shared` lays the tables out again.
- Queue fields are selected only by the authored full query and only for enabled queues (the saved `queues` setting, default Trunk and GitHub); with none the query is unchanged, and previews, the request query, and the reviewed query never select them. GitHub's queue wins over Trunk's; Trunk text prpr does not recognize is `QueueUnknown`, never a guessed state. Detail is capped single-line text and Trunk URLs pass `safeTrunkURL`. `paneQueue` shares the authored list and change tracker with `paneMine` (`tracker`, `inPane`), so a move between them is never a gone row; it is drawn only with rows, ordered passed, failing, testing, queued, submitted, unknown, and beside other filled panes its table takes no more than its rows. When the focused pull request moves between `paneMine` and `paneQueue`, `keepingSelection` moves focus and the selection with it, so details, `o`, and `y` keep acting on it. A pull request Trunk removed returns to `paneMine` tagged `queue failed` or `queue canceled`; a Trunk comment whose first line matches no state but that holds the template's unchecked submit box is the template, never an entry. Trunk drops `<!-- Trunk Merge -->` when it edits the template into a state, so a `trunk-io` comment without it is read only when its first line matches a state, and is otherwise another comment. Queue rows count in no attention category and never alert, except a removal for failed tests, and failing CI or changes requested while submitted. The legend's Queue entries (section, and the Nerd Queue header) appear only while the queue pane is drawn or a removed tag is on screen, so with queues off it is unchanged. There is no Trunk token or API.
- The merged list is the viewer's authored pull requests from `viewer.pullRequests(states: [MERGED], orderBy: UPDATED_AT desc, first: 2N+10)`, selecting only `id number title url mergedAt mergedBy repository additions deletions`, sorted by `mergedAt` (ties in fetch order) and cut to N, the saved `merged` (`app` key; 0, 3, 5, 10, or 20; default 5; 0 runs no query). Every full fetch, complete or incremental, runs it beside the other lists, never cached; previews never do; its failure fails the fetch and cancels the other half, the first failure reported. An authored pull request also in the merged list is dropped from the returned snapshot (not the cache), so it is never in both. `paneMerged` draws it, only with rows, with its own change tracker (`listMerged`, in `allLists`); `movedOn` keeps an authored pull request that appears in it from being a gone row, and nothing that leaves it is gone. Merged rows count in no attention category, not in the title, never alert, and cannot be snoozed or nudged (`z`, `R`); repository scope and search apply, quick and category filters never match them. Changing N starts a full fetch whose result resets the change baseline (`settingsBaseline`). It has the lowest layout priority: `framePlan` draws it (`paneSpecs` marks it `leftover`) only when `leftoverRoom` (the lines left after the open-list panes (`openPanes`) each take a title and all their rows, at least `minDualTableHeight`, and its own title) is at least `minDualTableHeight`; its table takes its rows up to that, the others share the rest as before, and it never counts toward single-pane mode or the legend's room. When it no longer fits, focus leaves it (`rebuildPRTable`). `H` (saved under the `app` key as `mergedCollapsed`; Settings' **Merged list**; a click on its title) collapses it (`toggleCollapsed`; `paneSpecs` marks it `collapsible`) to its title line: then `framePlan` draws it whenever the open-list panes keep their smallest tables (`openPanesNeed`) with a line to spare, it takes no table lines, and `framePlan.focusable` (focus fallbacks, Tab, `setFocus`, `keepSelection`, and fetch and snooze wakes) leaves it out, so it never has focus; hit testing gives its title alone.
- Snoozes are saved per account under its preferences key as `snoozed` (the account's object form); restoring never writes, an unreadable entry is skipped with a warning and kept as written until snoozes are saved. A snooze wakes on time (a timer for the earliest end, at most `snoozeCheckInterval` ahead, `snoozeGeneration` dropping older ticks; every full fetch checks too), on `z` in the Snoozed pane, or when a wake signal (`snoozeSignals`: ready, failing CI, changes requested, approved, conflicts, queue removal; for review rows needs-you and a pending request, or a normal or urgent nudge newer than the snooze's recorded `nudged` time) turns true that the last full fetch did not hold; unknown data keeps what was seen, and new activity, comments, bots, and `updatedAt` never wake. "Until activity" ends after `activityLimit`. Snoozed rows count in no category, not in the title, and never alert; a fetch or timer wake sends one notification, except on an account's first fetch and for snoozes already past when they load. A snoozed pull request that closes is a gone row in Snoozed and its snooze is deleted; one that merges moves to Merged instead (`movedOn`), its snooze deleted too. Previews never wake, record, or delete a snooze, and preview and gone rows cannot be snoozed. `z` keeps focus in its pane; fetch and timer wakes move focus with the selected pull request (`keepSelection`).
- A nudge is a comment on an authored pull request whose last non-empty line is exactly `<!-- prpr:nudge v1 urgency=(low|normal|urgent) to=<login>(,<login>)* -->` (`github/nudge.go`), every login valid; anything else is not a nudge, and the text above the marker is never read except its quoted note. Only comments by the pull request's author count, and only for the logins in `to=`. A row's nudge (`github.PullRequest.Nudge`, set only by a full fetch) is the latest one naming the viewer among the `activityItems` timeline items, and ends when the viewer reviews or comments at or after it; a later nudge replaces it. The mentions search `is:pr is:open mentions:@me -author:@me archived:false updated:>=<30 days ago> sort:updated-desc` reads one page of `mentionsLimit` (`pageSize`, 25) without `--paginate`, never more, in complete and incremental fetches alike; it keeps only rows with an active nudge that neither the request nor the reviewed search lists (request wins, then reviewed), placed by `ReviewStatus` when the viewer reviewed, else `ReviewNudged`. `X` dismisses a nudge by its exact time: dismissals are saved per account under its preferences key as `dismissed` (the account's object form) with `nudged` (older `requested` entries are ignored), unreadable entries are skipped, and a full fetch prunes those whose row no longer has that nudge. A dismissed nudge does nothing (no marker, order, count, alert, or wake) and keeps the selection; a dismissed `ReviewNudged` row is drawn, ordered, and counted as waiting. A nudge in effect shows its icon in the review pane's mark column: low steady, normal and urgent alternating with the row's change mark (`nudgeBlinkInterval`, `nudgeGeneration` dropping older ticks, the chain stopping when none blinks), uncolored since emoji ignore foreground colors; the column is two cells wide only while one is shown. The details add a **Nudged** row. The note is another user's text: it is cleaned on reading (one line, control and format characters and line and paragraph separators replaced, capped at `nudgeNoteMax`, 200 runes) and shown only in the details' **Nudged** row, never in a notification, the title, or the status line. Previews never read, show, alert on, or record nudges.
- `R` (nudge reviewers) posts prpr's only GitHub write: a nudge comment. It acts on an authored row only (not preview, gone, review, or merged rows), reads the pull request's `latestReviews`, `reviewRequests`, and the author's past nudges (`comments(last: 50)`) with a single-pull-request GraphQL query when pressed or when the details show an authored row (never in a fetch; it selects neither `search(` nor `mergeStateStatus`), and offers user reviewers other than the author, then users whose review is requested and who have not reviewed, then the other members (`members(first: 100, membership: ALL)`) of requested teams, which never start chosen; each person shows their latest review and their last nudge (`nudged <age> ago (<urgency>)`). The form is prpr's own list, not huh: a group of reviewers and requested people, then a group per requested team (code owners, then smaller teams, first), a person in several teams under each with one shared choice, and a panel (a line under `rerequestPanelMin` columns) marking each code-owner team covered by a chosen member or a member's approval of the head commit; GraphQL errors only under `reviewRequests` or `onBehalfOf` (a team gh cannot read without `read:org`) leave the rest offered and are counted and named, while any other error fails the lookup. Pending reviewers with no review, and reviewers whose latest review is not of `headRefOid` and is not an approval, start chosen; approvers never start chosen. `u` cycles the urgency (default normal), and `n` edits an optional note (Enter or Esc leave it) that `FormatNudge` makes one line without control or format characters, capped at `nudgeNoteMax` runes. A reviewer's state is their `latestOpinionatedReviews` entry when they have one, else their `latestReviews` one; staleness comes from the latter when present. Submitting reads the reviewers again before sending; a chosen reviewer whose latest review (`submittedAt`, both lists) is newer than the form showed, whatever the verdict, or who is no longer offered, is skipped and named in the notice, and a failed re-read sends nothing. Sending is an explicit form submit and a single `POST` to `repos/<owner>/<repo>/issues/<n>/comments` with `-f body=<comment>` through `Client.output`, so it runs as the pinned account with the token only in `GH_TOKEN`; the repository, number, and every login are validated first. Esc cancels and it never requests the mouse. A nudge changes no review state. Lookups and results from an older `accountGeneration` are dropped, a lookup another notice replaced opens nothing, and submitting re-checks that the pull request is still listed.
- Every column is a `columnSpec` in its pane's `paneSpecs` entry, in drawn order; ranked columns (statistics, Detail, From, Merged by) are kept in `rank` order while the PR name keeps `minStatsNameWidth` (statistics drop Size, Comments, Review, CI, Bots, Age; **Review requested** ranks Review last, so it drops first), and stay in drawn order.
- The list's help line shows enabled short keys, dropped from the end to fit, then pinned keys (`?`, `q`) that never drop; keys that apply only now (`esc`, `X`, `x`) lead it. `?` opens the help overlay, which lists every list key in `listGroups`, faint while disabled, and while open takes every key: `?`/Esc close it, line keys scroll it, others are ignored. A new list key belongs in a group (`TestHelpOverlayListsEveryListKey`).
- The status line's left side is, by priority: a preference error or notice, the selected row's change summary, then its `rowStatus` facts, dropped from the end to fit; the quota stays right-aligned. Like the details, `rowStatus` names a blocker only when the data proves it.
- The attention summary writes each category as `[n]` then its icon and count, shortening labels one at a time, the longest first, then dropping them all, until it fits.
- Every configured bot is judged by one rule, with no bot-specific text parsing: unresolved, non-outdated threads it started are concerns; then a matching head-commit check run that is unfinished or failed; then whether its latest review, comment, or non-👀 reaction is at or after the head commit date. With no bots configured, queries select none of the bot fields.

## Tests and interactive changes

- Follow existing tests: literal JSON decoder fixtures, direct TUI-message tests, and real preference stores under `t.TempDir()`.
- Assert deterministic, consumer-visible behavior. Do not pin prose, screenshots, incidental formatting, or implementation details.
- TUI behavior changes require a real terminal/PTY smoke in addition to unit tests. Exercise selection, empty scopes, resize, picker cancellation, and links as relevant to the change.
- Do not perform live login or mutate a developer's GitHub or user configuration during checks.
- For isolated Linux smoke runs, put a fake `gh` first on `PATH` and use a temporary absolute `XDG_CONFIG_HOME`. An explicitly requested live, read-only smoke must preserve the existing GitHub CLI configuration with `GH_CONFIG_DIR`.

## Change discipline and repository hygiene

- Reuse existing helpers and components. Keep changes scoped; add an SDK, alternate credential store, compatibility alias, or framework only for a concrete requirement.
- Never force-add `.devcontainer/project-adhd`, generated environment files, credentials, binaries, or preference files. Keep personal PR and repository data out of public commits.
- Do not add instructions tied to an agent vendor or local development setup. Do not make GitHub mutations or commit/push unless the user requests them.
